01 Executive Summary: Multi-Institution ERP Foundation

The Sohan Soft Tech ERP is designed and engineered strictly as a Multi-Institution Enterprise System. It is not tailored to, nor hardcoded for, any single educational institution. Any authorized Administrator or Super Administrator can dynamically provision new institutions through the platform governance lifecycle.

Every entity in the operational database—including Admins, Teachers, Staff, Students, Academic Years, Departments, Courses, Classes, Sections, Subjects, Timetables, Attendance Records, Assignments, Internal Assessments, Examinations, Gate Logs, and Grievances—is architecturally bounded by an institutionId foreign key. The system enforces strict multi-tenant data boundaries ensuring that Institution A can never access, view, or mutate the data of Institution B.

Verification Confirmation: The underlying PostgreSQL database schema already features institutionId String @db.Uuid foreign keys across all 28 operational models with compound tenant unique indexes (e.g. @@unique([institutionId, rollNumber]), @@unique([id, institutionId])). The multi-tenant database foundation is fully present and strictly normalized.

02 Multi-Institution Architecture & Data Isolation

The overarching tenant hierarchy organizes every institutional resource strictly beneath the primary tenant boundary:

PLATFORM SUPER ADMIN (Global Governance) │ ┌─────────────────────────────────┴─────────────────────────────────┐ ▼ ▼ INSTITUTION A (Tenant A) INSTITUTION B (Tenant B) (id: inst_uuid_a, code: 'APEX') (id: inst_uuid_b, code: 'HORIZON') ├── Institution Admin A ├── Institution Admin B ├── Departments & Courses A ├── Departments & Courses B ├── Classes & Sections A ├── Classes & Sections B ├── Teachers & Staff A ├── Teachers & Staff B │ └── Allocated Subjects & Timetable A │ └── Allocated Subjects & Timetable B └── Students A └── Students B ├── Class/Section Enrollment A ├── Class/Section Enrollment A ├── Classroom Attendance Records A ├── Classroom Attendance Records B └── Assignment & IA Marks A └── Assignment & IA Marks B

Core Tenant Isolation Rules

  • Rule 1 (Institutional Boundary): Teacher A (Institution A) can never access Student B (Institution B), nor view Institution B's timetables, classes, or attendance logs.
  • Rule 2 (Admin Scope): Admin A is cryptographically restricted by session token to session.institutionId and cannot administer Institution B unless possessing explicit Super Admin privileges.
  • Rule 3 (Faculty Scoping): Within Institution A, Teacher A can only access students enrolled in sections assigned to Teacher A via the timetable or faculty allocation.
  • Rule 4 (Student Scoping): Student A can only view their own profile, attendance, timetable, assignments, and exam results, strictly within Institution A.

03 Lifecycle Audit: Student & Teacher Creation Flows

1. Student Creation Lifecycle Flow

When an Administrator creates a Student via POST /api/admin/students & createStudent() in institution-admin.service.ts:

ADMIN CREATES STUDENT (/api/admin/students) │ ├─ 1. Extracts institutionId strictly from verified session (resolveAdminContext) ├─ 2. Validates rollNumber uniqueness within this specific institution: │ tx.student.findFirst({ where: { rollNumber, institutionId } }) ├─ 3. Atomic User Provisioning: │ tx.user.create({ data: { institutionId, email, fullName, role: 'STUDENT', isActive: false } }) ├─ 4. Atomic Student Record Insertion: │ INSERT INTO students (id, institutionId, userId, rollNumber, currentCourseId, currentClassId, currentSectionId...) ├─ 5. Academic Enrollment History Creation: │ tx.studentEnrollmentHistory.create({ data: { institutionId, studentId, academicYearId, classId, sectionId } }) └─ 6. [DISCOVERED GAP]: Legacy "Enrollment" table row is NOT provisioned. Because AttendanceRecord and AssessmentRecord require a foreign key to "Enrollment", createStudent() MUST provision an active Enrollment record alongside studentEnrollmentHistory.

2. Teacher Creation Lifecycle Flow & The Duality Gap

When an Administrator creates a Faculty Member via POST /api/admin/staff & createStaff():

ADMIN CREATES FACULTY MEMBER (/api/admin/staff) │ ├─ 1. Extracts institutionId strictly from verified session (resolveAdminContext) ├─ 2. Atomic User Provisioning: │ tx.user.create({ data: { institutionId, email, fullName, role: 'TEACHER', isActive: false } }) ├─ 3. Atomic Teacher Creation: │ tx.teacher.create({ data: { institutionId, userId, department: data.departmentId, employeeId... } }) └─ 4. [DISCOVERED DUALITY GAP]: The schema contains BOTH "Teacher" (used by auth & timetable) AND "Staff" (used by academic HOD/department relations). createStaff() currently provisions ONLY "Teacher", leaving "Staff" empty. Consequently, Section.classTeacherId and Department.hodStaffId cannot be linked to the newly created faculty. REQUIRED FIX: createStaff() must atomically provision BOTH Teacher and Staff records sharing userId and institutionId.

04 Student ↔ Teacher Operational Connection

An audit of the codebase confirms the exact structural relationship linking Students and Teachers across the institution:

The TimetableSlot Operational Bridge CONFIRMED IN CODE

In this ERP, Teachers and Students are not directly coupled by an artificial foreign key. Instead, they are dynamically bound through TimetableSlot within the same institutionId: 

INSTITUTION (institutionId)
    ├── TimetableSlot
    │     ├── teacherId ──────► Teacher (tied to User)
    │     ├── subjectId ──────► Subject
    │     ├── semester  ──────┐
    │     └── section   ──────┴─► Matches Student.currentSemester & Student.currentSection
    └── Students (where student.institutionId == slot.institutionId)

How Teacher Resolves Students: In teacher.service.ts, getSectionStudents(sectionId) extracts (semester, section) from the allocated slot and queries: prisma.students.findMany({ where: { institutionId, currentSemester: semester, currentSection: section, status: 'ACTIVE' } }).

How Student Resolves Teachers: In app/api/student/timetable/route.ts, the student queries slots matching their current semester and section, joining teacher.user.fullName to render their instructor's name for each subject.

1. Current Disconnects Impacting Multi-Institution Operations

Area Severity Current Problem in Codebase Multi-Tenant & Operational Impact
Admin Attendance UI P0 — CRITICAL app/admin/attendance/page.tsx reads from in-memory lib/store.tsx instead of /api/admin/attendance. Admin cannot view live attendance marked by teachers in their institution. High-level institutional attendance statistics remain frozen on dummy data.
Admin Timetable UI P0 — CRITICAL app/admin/timetable/page.tsx saves slots into React state without persisting to POST /api/admin/timetable. Newly configured classes and instructor assignments never reach timetable_slots, leaving teacher and student schedules unlinked in the database.
Faculty Model Duality P0 — CRITICAL Admin createStaff() provisions Teacher, but leaves Staff empty. Breaks HOD departmental relations and class teacher section assignments that foreign-key reference Staff.id rather than Teacher.id.
Student Enrollment Provisioning P0 — CRITICAL Admin createStudent() creates studentEnrollmentHistory but does not create an active row in legacy enrollments. Subsequent attendance marking or IA marks entry fails foreign key constraints on AttendanceRecord.enrollmentId.
Teacher Service In-Memory Fallbacks P0 — CRITICAL teacher.service.ts uses in-memory store and falls back to demo-school if session lookup fails. Ephemeral memory is lost on serverless restarts; risk of fallback to demo teacher across institutions if tenant slug is omitted.
Admin Auth Dev Fallback P1 — HIGH lib/security/admin-auth.ts allows unauthenticated access in non-production defaulting to inst_apex. Allows unauthenticated API calls to inspect or mutate institutional records if STRICT_ADMIN_AUTH is disabled.
